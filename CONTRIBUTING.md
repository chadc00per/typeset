# Contributing

Bug reports, ideas and pull requests are all welcome.

```sh
npm install
npm test            # builds js/dist/, then runs every test under js/tests/
npm run lint
npm run typecheck   # js/src/index.d.ts

python3 -m venv .venv && .venv/bin/pip install -U "pip>=25.1" && .venv/bin/pip install -e ".[all]" --group test --group lint
npm run test:python   # python/tests against conformance/
npm run lint:python   # ruff, and mypy over the stubs
npm run conformance   # after an intended behavior change: regenerates the contract
```

This repository holds two packages that must store every value identically, one per
language, plus the contract between them:

| | JavaScript (npm) | Python (PyPI) |
|---|---|---|
| Manifest | `package.json` | `pyproject.toml` |
| Package | `js/src/` (the reference) | `python/chadc00per_typeset/` |
| Tests | `js/tests/` | `python/tests/` |
| Scripts | `js/scripts/` | `python/scripts/` |
| Build output | `js/dist/` (not committed) | `dist/` (not committed) |

**Shared:** `data/` (pinned reference data, and `catalog.json`, every type's metadata) and
`conformance/` (the JavaScript answer for each input). Both test suites check them.

## Layout

A helper lives in `lib/` only when two or more types use it; anything one type
needs stays in that type's file.

## Type files

Every file in `js/src/types/` has the same shape:

```js
// color: what the type stores and the rules it applies, in a sentence or two.
import { fail } from '../lib/errors.js';
import { text } from '../lib/text.js';

export const definition = {
  name: 'color',
  description: 'Hex, RGB or HSL color with optional opacity; canonical hex',
  example: '#4caf50',
  control: 'color'
};

export function normalize(value, path, type) {
  const raw = text(value, path, type);   // string, length cap, control characters, trimmed
  return /^…$/.test(raw) ? raw : fail(path, type);
}

// optional:
export const methods = { extra };                          // becomes Color.extra()
export function validate(value, path, type) { … }          // replaces the registry's check
```

`definition` holds `name`, `description` and `example`, and only the fields that
differ from their defaults: `storage` (`'string'`; also `'number'`, `'array'`,
`'object'`), `constraints` (`'length'`; `'value'` for numbers), `collation`
(`'lexical'` for strings, `'numeric'` for numbers, otherwise `'none'`), and the picker's `control` (`number`, `select` or `text` by
storage), `step`, `options` (a select's fixed choices) and `className` (the
constructor name, when capitalizing the name won't do). The Title Case `labels`
and the nouns refusals use live in `labels.js`, and the `jsonSchemas` details in
`definitions.js`, so they read alike across types. A noun is the label lowercased,
acronyms kept; add an override to `NOUNS` only where that doesn't read well in
"must be a valid …".

- **`normalize(value, path, type)`** returns the canonical stored value. `type` is
  the type's noun, only for messages. Helpers take `(raw, path, type)` in that order.
- **Refuse with `fail(path, type, detail?, code?)`**. It throws a `ValidationError`
  that reads "`<path> must be a valid <noun> (<detail>)`"; `type` may also be another
  type's name (`fail(path, 'currency')` reads "currency code"). `check()` relies on
  that format to split out the path. `code` is `'invalid'` unless the value is a
  number outside the type's bounds (`'range'`); `check()` reports `'required'` for
  missing or empty input by itself. Never throw a `TypeError` for bad input; that
  class means a bug. (`lib/point.js` names a shape instead, as in "`must be an
  [x, y] pair`", and keeps the "`<path> must be`" lead.)
- **Start string input with `text()`**. Its options state the grammar's limits:
  `max` (default `MAX_INPUT`, 8192), `control` (`CONTROL`, which refuses tabs,
  `CONTROL_EXCEPT_TAB`, `CONTROL_EXCEPT_WHITESPACE`, or `null`), and `empty`.
- **Use the shared grammars.** `DECIMAL` is a number the way form input spells it.
  `EXACT_DECIMAL`, `exactDecimal()` and `decimalText()` cover decimals that must
  not round through floating point.
- **`validate()` comes from the registry**: a stored value must equal what
  `normalize()` returns for it. A type exports its own `validate` only when that
  rule doesn't fit.
- **A stored value is a data format.** Changing what a type returns for an input
  it already accepted breaks existing data, so treat that as a breaking change.

## Style

- Fixed module-level data (regexes, lookup tables, value sets, limits) is
  `UPPER_SNAKE_CASE`. Functions and lazily filled caches are `camelCase`.
- Each file opens with a `//` comment naming what it holds, with no blank line
  before it. `/** */` is for exported API in registry.js; use `//` elsewhere.
- Keep comments short, and only where the code doesn't already say it. Files that
  mirror each other across languages say so at the top; keep them in step.
- ESLint (`eslint.config.js`) and `.editorconfig` cover the rest.
- Python mirrors the JavaScript: a refusal is `return fail(...)` as in JS,
  constants are `UPPER_SNAKE_CASE`, and any JavaScript behavior Python lacks
  (string lengths, trimming, number spelling, UTF-16 indexing) lives in
  `python/chadc00per_typeset/_lib/js.py`, never as a private copy in one
  module. Write invisible characters in Python source as escapes or code
  points, not literally. Ruff (`[tool.ruff]` in `pyproject.toml`) checks the rest.

## Adding a type

1. Create `js/src/types/<name>.js` with its `definition` and `normalize()`, moving
   anything it shares with another type into `js/src/lib/`.
2. Import it in `js/src/definitions.js` and add it to `ORDER`, in picker order.
3. Add the constructor to the export list in `js/src/index.js`, and to the type
   union and the `export const` list in `js/src/index.d.ts`. The constructor name
   capitalizes each word, an acronym is one word (`Url`, `Isbn`) and each
   coordinate letter is its own word (`XY`); set `className` when the plain
   capitalized name doesn't follow that rule.
4. Create `js/tests/types/<name>.test.js` with accept/refuse cases.
5. Add its label to `labels` in `js/src/labels.js` (and a noun to `NOUNS` if the
   derived one reads badly), any JSON Schema detail to `jsonSchemas` in
   `definitions.js`, its accepted input kinds to `TypeInputs` and its value type to
   the `…Value` list in `index.d.ts`, and a row to TYPES.md.
6. Run `npm run conformance` to add its catalog entry and vectors.
7. Port it to `python/chadc00per_typeset/_types/<name>.py` (and any new helper to
   `python/chadc00per_typeset/_lib/`), mirroring the JavaScript line for line. The module
   has only `normalize(value, path, type)` and optionally `validate` and
   `methods` (snake_case names). Add the class to `python/chadc00per_typeset/__init__.py`
   and run `python3 python/scripts/generate-python-stubs.py`.

`npm test` and `npm run test:python` fail if any of these steps is missed.

A type that needs a heavy third-party library is optional in both packages: the
lite browser builds list it in `omittedTypes` (`js/src/lib/vendor.lite.js`), and
Python lists it in `_EXTRAS` (`_registry.py`) with the extra that installs it.
Without the dependency, every call to the type raises, whatever the input.

The code types (`javascript`, `python`, `html`, `css`, `svg`) check source
with `js/src/lib/code.js`, which Python doesn't port: it runs that file, bundled
with its parsers into `python/chadc00per_typeset/_parsers.js`, in an embedded
V8. After changing `code.js` or a parser's pinned version, run `npm run
parsers` to rebuild the bundle (`js/tests/parsers.test.js` fails until you do), then
`npm run conformance`. Parser versions are pinned exactly in `package.json` and
the V8 binding in `pyproject.toml`; upgrade them only together with that
rebuild. A dependency that publishes no license file needs its repository's copy
in `js/scripts/licenses/`.

A type whose accepted inputs must differ by language (only `function`, which
holds each language's own source code) sets `runtimeSpecific` in its
`definition`, with what Python describes differently (`{ python: { example } }`).
`npm run conformance` then lists it in `data/catalog.json` and writes its vectors
as `<name>.js.json`; Python skips them, so its port needs its own tests in
`python/tests/test_<name>.py`. Keep every other rule the type has (trimming,
line endings, refusal messages) the same in both languages.

## The docs are tested

`js/tests/readme.test.js` and `python/tests/test_readme.py` run the README's
examples: every `js` and `python` code block runs, and a line ending in
`// → value` (`# → value` in Python) checks the expression before it equals
`value`; `// → throws Name: message` (`# → raises Name: message`) checks the
error. `ts` and `tsx` blocks are type-checked, strict. Every TYPES.md row's
`input` → `stored` sample is checked in both languages. Write new examples the
same way, so they can't drift from the code; `sh` and `html` blocks aren't run.

## Data

Pinned reference data ships in `data/`, shared by both packages: CLDR 48
validity tables, Unicode 17 emoji, the ISO 4217 currency list, the IANA
top-level domains, and the time zone, language and locale alias answers of
ICU (recorded with its version), so no runtime's own ICU changes a stored
value. `js/scripts/` and `python/scripts/` regenerate each from its source.

The contract between the languages is `data/catalog.json` (every type's
metadata and JSON Schema, from which the Python package builds its classes) and
`conformance/vectors/<type>.json` (the JavaScript reference's answer for each
input: canonical value, refusal path, message and code, and stored-value
verdict). `npm run conformance` regenerates both; both test suites check them.

libphonenumber's numbering-plan metadata is released separately for npm and
PyPI, so both packages pin the same release (`google-libphonenumber` 3.2.48,
`phonenumbers` 9.0.40–9.0.42, which agree on every number checked). Upgrading
one means upgrading the other; the phone tests hold numbers that changed
between releases, so a mismatch fails CI.

## Keeping the languages identical

A behavior change is made in JavaScript first, then `npm run conformance` records it
and the Python port follows until `npm run test:python` passes. CI fails if
the contract is stale. When porting, `python/chadc00per_typeset/_lib/js.py` lists the Python
habits that silently change answers: `$` matching before a final newline, the
Unicode-aware `\d`/`\s`/`\w`, `re.IGNORECASE` folding `K` (U+212A) to `k`,
`len()` counting code points instead of UTF-16 units, banker's `round()`,
`%` on negatives, `str(float)`, and `bool` being an `int`. Nothing may depend on
the runtime's ICU: pin such answers in `data/` with a generator script.

## Pull requests

1. Fork, branch, change.
2. If you change behavior, change it in JavaScript first and record it with
   `npm run conformance`, then make the Python port pass (see above).
3. Every command at the top of this file passes.
4. New behaviour comes with a test, and a line in the docs if users will notice it.
5. Sign off every commit (see below).
6. Leave the version numbers and `CHANGELOG.md` versions alone, and don't push tags: a
   maintainer does those when releasing.
